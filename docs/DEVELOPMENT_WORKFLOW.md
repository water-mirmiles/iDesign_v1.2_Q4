# 开发流程

最后更新：2026-10-11 · 参照 iAMZ 的唯一源码、批量推送和分层验收流程。

| 阶段 | 必做动作 | 进入下一阶段的条件 |
| --- | --- | --- |
| 需求 | 读文档/status；在 ITERATIONS 建 ITER，关联 REQ；较大任务建需求 Issue | 目标、范围、验收和不确定点明确 |
| 设计 | 在 PRD 明确状态/字段/交互；涉及界面列截图场景，涉及接口列真实契约 | 可观察的验收条件，不假定不存在的接口 |
| 实施 | 从已验证基线建 feature/fix/chore 分支；小步修改，保留本地恢复点 | 改动限于授权范围，保留用户作品 |
| 文档 | 本轮就地同步 PRD/FEATURES/ITERATIONS/CHANGELOG，环境变化同步 README/TESTING | 文档可解释最终行为与实际边界 |
| 验证 | npm run check；提交后 docs:sync；必要视觉、存储/导出、真实外部验收 | 检查通过或明确受阻，不删测试绕门禁 |
| 推送准备 | 汇总提交、文件、证据、限制和回退点，保持 PR 草稿 | 用户明确授权该批推送；iAMZ 两阶段约定见 AGENTS |
| 远程验证 | 不强推；推候选分支、建/更新 PR，检查该 head 的 CI | head 对应 CI 通过；评审核对文档与行为 |
| 用户验收 | 给具体操作步骤，记录结论及退回原因 | 用户明确接受；否则保留待验收 |
| 合并/发布 | 获得对应授权；重新核对 head/checks，版本、包/校验和与变更一致 | 只合并/发布被授权且已验证的版本 |

## 文档即时更新矩阵

| 变更 | 同批必须更新 | 条件更新 |
| --- | --- | --- |
| web 代码、样式或参考素材 | PRD、FEATURES、ITERATIONS、CHANGELOG | README 使用方式、TESTING 证据/用例、ASSET_SOURCES 来源变化 |
| scripts、tests、CI、package 配置 | README、TESTING、ITERATIONS、CHANGELOG | PRD/FEATURES 的能力或门禁受影响时 |
| 仅需求/原则 | 对应文档、日期与理由 | ITERATIONS 记录本轮决策；已有代码受影响则列后续任务 |
| 合并/标签/交付 | VERSIONING、ITERATIONS、CHANGELOG | README/TESTING 最新交付快照 |

“即时”指需求确认时、行为变化时、本轮提交前和交付时同步更新，不依赖后台定时。CI 只能检查文件是否同步，不替代内容评审。代码 PR 缺必需文档时失败；不给任意跳过开关。每轮结束提供变更摘要和证据，避免 README 堆叠所有历史。

## 分支与提交

- `main`：稳定基线，日常变更走 PR。空仓库可建立最小初始化提交，本次已授权。
- `chore/project-foundation`：首轮工程候选；尚未合入时后续工作从该基线建分支，并把依赖写清。
- `feature/<主题>`、`fix/<主题>`、`chore/<主题>`：一个明确任务；提交消息用 `feat:`、`fix:`、`docs:`、`chore:`、`test:` 并写影响对象。
- 本地 `baseline-original` 保存此次整理前可运行原型；候选标签用 `v0.1.0-foundation-rc1`，不等于用户已验收。
- 主分支服务器保护未配置前，CI 不会自动禁止管理员合并；实际配置状态见 VERSIONING。

## 评审和授权

PR 说明具体问题、最终行为、REQ/ITER、验证证据、模拟边界和回退点。未通过检查、外部能力未验收、用户未接受各自独立标明。用模拟测试覆盖协议失败路径是工程验证；真实接口需真实响应和输出证明。

推送、合并、收费服务与生产部署分别授权。当前用户明确要求建立并同步 GitHub，授权本次初始化和候选 PR；不自动合并。后续“打包推送”按 AGENTS 的准备 → OK → 推送流程执行。
